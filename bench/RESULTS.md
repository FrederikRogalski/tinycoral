# Coral Edge TPU: Google's native stack vs. our tinygrad stack

**Setup:** MacBook (Apple M1 Pro-class, macOS 26), Coral USB Accelerator on USB 3 (5 Gb/s).

**Native stack:** edgetpu_compiler 14.1 + libedgetpu 16.0 (feranick's arm64 build of google-coral/libedgetpu) + tflite_runtime 2.18. This is the official Coral software stack.

**Ours:** a pure Python USB driver on tinygrad's libusb bindings, and programs from our own code generator (MobileNet: Google's compiled program, run by our driver). No libedgetpu, no TFLite, no compiler at runtime.

Both are timed from Python, 300 runs, median, same random input. Outputs are compared by hash.

Google's stack for the comparisons runs in its own environment: `.venv-native` with tflite_runtime 2.18, and libedgetpu builds for both clocks in `.native/lib/std/` and `.native/lib/max/`. `bench/hw_session.py` runs the hardware tests and the benchmarks one by one and stops when the device stops answering.

|---|---|---|

| 288 x 288 | 0.215 ms | **0.176 ms** |

- The win comes from issuing every USB transfer asynchronously and up front (all bulk INs queued before the OUTs), and from skipping the TFLite interpreter.

Reproduce: `python bench/fc.py` (`--max` for the max clock).

## Our code generator on hardware
All programs are generated by us from the decoded ISA. Each is checked bit-exact against the reference on random weights, inputs and quantizations.
| generator | byte-identical to edgetpu_compiler (offline) | on the device |
|---|---|---|
| FULLY_CONNECTED `gen_fc` | 355/355 table shapes, 1918/1920 random shapes | 50/50 random shapes bit-exact, at any 256-byte-aligned parameter offset |
| FC on other tiles (translated) | equals ring_mesh.translate_tiles | 9/9 bit-exact |
| FC with only the compute tiles moved (no compiler equivalent) | n/a | 15/15 bit-exact |
| batched 1x1 conv `gen_conv1x1` | all TinyStories shapes x 5 batch sizes, 900+ random shapes, 120/120 co-compiled placements | 12/12 bit-exact, weights on tiles 0/5/9/14 at arbitrary offsets |
| plain tinygrad `qlinear` → kernel selection → our programs | n/a | bit-identical to DEV=CPU |
| fused FFN block, on-chip argmax, our placement plan (`coral/codegen/fused.py`) | 24/24 FFN, 15/15 argmax, all 113 programs of the co-compiled set | the whole LLM, see below |

- **Rounding:** the TPU rounds half to even. We measured it with exact .5 ties: thousands per test, 100% half-to-even, FC and batched alike. Our reference used TFLite's half-away-from-zero until then.
- **The whole LLM on our own programs:** every program generated by `coral/codegen*.py` and placed by our plan, no edgetpu_compiler output anywhere. TinyStories-15M decodes at 61 / 333 / 666 / 1308 / **1815** tok/s at batch 1 / 8 / 32 / 128 / 256, the same as with the compiler's programs. The 256 stories are identical text.
- **Batch 1, every matmul on our own programs:** all 24 TinyStories matmuls packed on chip with our planner and tile-shifted programs give 62.3 tok/s, the same as the compiler's co-compiled programs (62.6).

Reproduce: the offline columns with `python -m coral.codegen.fc` (`.conv`, `.fused`, ...), the device column with `test/test_hw_*.py`.

## Things the native compiler can't do / gets wrong
- **No batched FC.** edgetpu_compiler maps FULLY_CONNECTED only with batch 1; batch > 1 stays on the CPU. Batched matmul has to be written as a 1x1 CONV_2D.
- **Slow 1x1 conv mapping.** For those convs the compiler's own cycle estimate implies ~256 MACs/cycle, i.e. 1 of 16 tiles. Measured: 20-34 GOP/s on a 4 TOPS chip.
- **Compiler crash.** A 1x1 conv with 128 positions, 768 in, 288 out fails with `Internal compiler error. Aborting!`.
- **Separately compiled layers evict each other.** Every program compiled on its own places its parameters at tile 0, offset 0.
  - Only when all layers go through one compiler call does it spread them over the 16 tiles. Then all 24 TinyStories-15M matmuls (6.3 MB) stay resident; we use these co-compiled programs.
- **Big streamed layers get re-streamed.** For the 32000x288 classifier (9.3 MB of weights), the compiler streams the weights once per chunk of 64 positions whenever the outputs don't fit on chip.
  - That is 2x at 128 positions and 16x at 256 positions with 16000 outputs (75 MB per call); 256 x 32000 doesn't compile at all.
  - We split the classifier so that every piece streams once.
- **No transformers.** It can't compile an LLM. We run TinyStories-15M with all 30 matmuls per token on the Edge TPU.

## LLM: TinyStories-15M (llama2.c), tinygrad, decoding throughput
Same model code for every backend (`examples/stories.py`; it loads the RoPE table as data, for every backend alike).

| batch | Mac CPU (tinygrad CPU, fp32) | Coral, our programs | Coral, edgetpu_compiler's programs (earlier) | Mac GPU (tinygrad METAL) |
|---|---|---|---|---|
| 1 | 68.8 | 61 | 62.6 | 316 |
| 8 | 316 | 333 | 330 | 2 212 |
| 32 | 560 | 666 | 654 | 6 633 |
| 128 | 623 | **1 308** | 1 269 | 22 198 |
| 256 | 640 | **1 815** | 1 852 | 28 000 |

Tokens per second. The Coral runs every matmul as uint8 on the TPU; attention, norms and RoPE run on the host. At batch 256 that is 2.8x the CPU column.

Reproduce: `DEV=CPU python bench/llm_batch.py float 1 8 32 128 256` (`DEV=METAL` for the GPU), `DEV=CORAL python bench/llm_batch.py fused 1 8 32 128 256`, and `python bench/numpy_llm.py 1 8 32 128 256` for the numpy baseline below.

**Which CPU baseline:**
- **"Mac CPU (tinygrad CPU)" is one core.** tinygrad's CPU backend compiles every kernel with clang and runs it single-threaded.
- **A strong multi-core baseline** is the same model in plain numpy (`bench/numpy_llm.py`): its matmuls go through Apple's Accelerate BLAS (AMX units, all 8+2 cores of the M1 Pro).
  - 138 / 1 201 / 2 652 / 4 677 / **5 435** tok/s at batch 1 / 8 / 32 / 128 / 256.
  - That is 3x the Coral at batch 256.
- **So on this laptop the Coral beats tinygrad's single-threaded CPU path, not the machine.** It is meant for hosts like a Raspberry Pi, whose CPU is a small fraction of an M1 Pro.
- **batch 1:** one FC program per matmul (24 per token), all weights resident.
- **batch ≥ 8:** every layer as 3 programs (fused qkv, wo, and the whole FFN block w1·w3·SiLU·mul·w2 as one program), all 6.3 MB of weights resident.
- **batch ≥ 64:** the classifier also runs as an on-chip block-argmax.
  - The vocabulary is the input image and the tokens are the weights; an 8x8 max-pool sends back the max of every block of 64 logits (128 KB instead of 8 MB).
  - The host recomputes the 4 best blocks per row exactly. On real activations (batch 256, 40 steps, 10 240 tokens), that picks the same token as the float argmax over all 32 000 logits 100% of the time, for 2.6 ms of host work per step (top-2 blocks: 99.7%, top-1: 97.4%).

**Where a batch-256 step goes (138 ms):**
- ~60 ms TPU for the 18 layer programs; mostly the qkv output over USB.
- ~40 ms streaming the 9.2 MB vocabulary.
- ~14 ms refining the argmax.
- ~14 ms host CPU kernels.
- The rest is Python/JIT overhead.

**Before the fused blocks:** 579 tok/s at batch 256. The 8 MB of logits and the 1536-wide FFN activations went back over USB each step, at ~55 MB/s device→host.

## An ordinary tinygrad CNN: MNIST (`examples/mnist.py`)
The model of tinygrad's `beautiful_mnist`: four convolutions (5x5, 5x5, 3x3, 3x3), ReLU, two batch norms, two max pools, one linear layer. It was trained in float with tinygrad on METAL: 98.93% on the 10 000 test images.

`coral.quantize(model, 256 training images)` makes the uint8 model:
- Both batch norms fold away. They sit behind a ReLU; their scales are positive, so the scale goes into the conv before and the shift through the max pool into the next layer's bias. Each fold is checked on the calibration data.
- Between every two layers there is only ReLU and max pool, so each pair shares one quantization. The ReLU becomes the requantization's clamp at 0, and what runs in between is an exact uint8 max pool.

| path | accuracy (10 000) | images/s |
|---|---|---|
| tinygrad float, host (clang, one core) | 98.93% | 272 |
| our uint8 model, host (DEV=CPU, plain tinygrad kernels) | 98.93% | 336 |
| **ours, stage 1:** every conv as im2col + one quantized matmul on the TPU (256 rows per call; first quantizer, 2 000 images) | 98.40% (= float on those) | 130 |
| **ours, stage 2:** every conv its own native CONV_2D program (up to 32 images per call as a tall image), TinyJit | 98.45% (2 000) | 728 |
| **ours, stage 3:** TinyJit fuses the whole network into one program from our generator (32 images per call), batch 1024 | **98.95%** (9 216) | **22 994** |
| Google: **the same uint8 model** exported to TFLite (`tools/export.py`), edgetpu_compiler + libedgetpu, std clock | 98.93% | 2 316 |
| Google, max clock | 98.93% | **2 615** |

- **Bit-identical:** Google's stack on the exported model and tinygrad on the host give the same 10 uint8 logits for all 10 000 test images.
- **Google's program** (`bench/mnist_google.py`):
  - All 7 ops land in one Edge TPU program.
  - Every invoke sends 57 KB of instructions (549 instructions: 70 ops, 17 max pools, 277 mesh transfers), 784 bytes of image, and gets 16 bytes back.
  - The compiler estimates 15 278 cycles (31 µs at 500 MHz); an invoke takes 383 µs. USB and the instruction upload dominate, not the arithmetic.
- **No batching:** with a batch dimension > 1 the compiler maps nothing ("Tensor has unsupported rank").
- **Batching anyway, with a tall image** (`tools/export.py`, `tall=B`): stack B images into one 28B x 28 image.
  - VALID convolutions and pools never mix two images' rows, and the linear layer becomes a 3x3 convolution over each image's last map. For the compiler it is an ordinary single-image model.
  - Same compiler, same runtime (max clock), and every logit is still bit-identical to tinygrad:

| images per invoke | images/s | ms per invoke |
|---|---|---|
| 1 | 2 578 | 0.39 |
| 8 | 12 072 | 0.66 |
| 32 | 24 178 | 1.32 |
| 64 | 25 884 | 2.47 |
| 128 | **26 127** | 4.90 |

  - At 128 images per invoke, 38 µs per image is close to the compiler's own estimate of the arithmetic (31 µs): the chip is busy, not the USB.
- **The same programs on our USB runtime** (`bench/mnist_runtime.py`, max clock): 3 102 / 13 640 / 23 242 / 23 903 / 25 210 images/s at 1 / 8 / 32 / 64 / 128 images per invoke, logits identical. That is faster than libedgetpu up to 8 per invoke and within 4% above. These are the numbers our own chain programs have to reach.
- **Stage 3, step by step** (`DEV=CORAL python examples/mnist.py`, batch 128 / 256 / 1024: 17 634 / 20 829 / 22 994 images/s):
  - TinyJit captures 11 kernels. Kernel selection and `select_glue` recognize 9 of them (4 convs, 2 copies, 2 max pools, the linear layer), and `coral/chain.py` fuses them into one call.
  - `coral/codegen/chain.py` writes one program for the whole network, byte-identical to edgetpu_compiler's for the same model at 1..32 images per call.
  - Only the input quantization and the logits' dequantization stay on the host.
  - That is 8.8x Google's own deployment of the same model on the same chip, and 33x tinygrad's single-core CPU path.
- **Our stage 1 is slow by construction:**
  - im2col multiplies the input 25x on the host and sends it over USB.
  - 100 images take 423 TPU calls.
  - Every intermediate activation comes back at ~55 MB/s.

Reproduce: `DEV=METAL python examples/mnist.py train` once, then `DEV=CORAL BS=1024 python examples/mnist.py` (`DEV=CPU` for the host rows). Google's stack: `DEV=CPU python bench/mnist_google.py build B` (B images per invoke), then `.venv-native/bin/python bench/mnist_google.py run max MODEL` with the printed model, and `CORAL_CLOCK=max python bench/mnist_runtime.py MODEL` for our runtime.

## tinygrad's CIFAR-10 speedrun model (`examples/cifar.py`)
SpeedyConvNet from tinygrad's `examples/beautiful_cifar.py`: 7 convolutions with residuals, GELU, batch norms and max pools, 4.3 M parameters. It was trained by the unchanged script on the M1 Pro's GPU in 40 minutes (89.4%). The batch norms are frozen to training-set statistics, because the script normalizes with each batch's own.

| path | accuracy (2 000 test images) | images/s |
|---|---|---|
| float, tinygrad on the host (clang, one core) | 90.20% | 43 |
| uint8 (coral.quantize folds all 6 batch norms), every conv and the linear layer on the TPU, TinyJit, batch 100 | **90.20%** | **130** |

- The three big convs (256→256, 256→512, 512→512) run natively with their weights split over 2, 3 and 5 tiles. All 4.3 MB stay resident and are uploaded once.
- GELU, the residual adds and the max pools run on the host between the TPU calls. Every activation goes to the host and back, which is the bottleneck.

Reproduce: `DEV=METAL python examples/cifar.py train` once, then `DEV=CORAL N=2000 python examples/cifar.py`.

## The whole TinyStories-15M transformer on the chip (`examples/stories_chip.py`)
One Edge TPU program per token runs all 6 layers: RMSNorm (as an L2 normalization, the weight folded into the next FC), qkv, RoPE, attention over the KV cache (softmax on the scalar core), wo, the residual adds and the FFN. Every instruction comes from our generator (`coral/codegen/layer.py`); edgetpu_compiler can't compile any of it.
- **The host's share:** the embedding lookup, the final RMSNorm, the classifier (32000 × 288 doesn't fit on the chip next to the layers), the sampling and the uint8 KV cache, which goes to the chip every call.

| batch 1 | tokens/s | per token |
|---|---|---|
| the matmul path: 18 TPU calls (qkv, wo, FFN per layer), attention / norms / RoPE on the host | ~70 | |
| **whole model on the chip** | **176.7** | one TPU call (USB included) 4.22 ms + host 1.28 ms |

- **On the device:** bit-exact against the program's numpy bit model at P = 1, 2, 64, 256. Per call: 1.63 / 1.88 / 3.22 / 7.59 ms.
  - In a 205-token generation, 199 calls were bit-exact. The others trace to a softmax value 9e-5 below a rounding tie: the scalar core's exp2/reciprocal are not exactly correctly rounded float32.
- **Quality**, teacher-forced on stories the float model wrote: perplexity 2.13 vs 1.88 in float, and 86.5% top-1 agreement. The matmul path, with only the matmuls in uint8, has 2.18.
  - The BOS token drives three residual channels to ±15, so position 1 gets its own quantization. With one shared quantization perplexity was 2.88.
- **Per call:** ~390 KB of instructions; the K/V upload grows to 886 KB at 256 positions.

Reproduce: `python examples/stories_chip.py` (`--check DIR` compares every call with the bit model), and offline `python examples/stories_chip.py --eval N` for the quality.

### Does uint8 hurt? (`bench/attention_quant.py`, before any of it ran on the chip)
A numpy simulation of TinyStories-15M at batch 1: every quantization point uint8 per tensor, with ranges calibrated on float runs; 8 stories the float model wrote (200 tokens each), teacher forced.

| variant | perplexity | top-1 = float |
|---|---|---|
| F float | 1.81 | |
| M matmuls uint8 (the matmul path) | 2.18 | 86.3% |
| A + attention uint8 (q, k, v, scores, softmax at 1/256, p·V) | 2.16 | 84.6% |
| N + RMSNorms on uint8 | 2.39 | 82.1% |
| R + the residual stream uint8 | 2.69 | 76.9% |

- Attention in uint8 costs nothing measurable; the norms and the residual stream cost some.
- Per-channel weights barely help: Mp 2.11, Ap 2.14, Np 2.34, Rp 2.60. The loss is in the uint8 activations, not in the weights.
- The attention on the chip multiplies elementwise, so every q·k and p·v product is rounded to uint8 before the sum (variant E). On 6 stories × 160 tokens: perplexity 2.33 vs 2.20 for A and 2.24 for M; top-1 agreement 82.7% / 83.2% / 84.2%.

Reproduce: `python bench/attention_quant.py 8 200` (variants M, A, N, R and the per-channel ones), `python bench/attention_quant.py 6 160 A,E,M`.
